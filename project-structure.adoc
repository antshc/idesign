= IDesign Project Structure Summary
:toc:
:toclevels: 3
:sectnums:

Goal: keep a *closed architecture* and apply DIP so that:
* High-level policy (Managers/Engines) depends on abstractions and stable models
* Low-level details (ResourceAccess) depend on those abstractions and models
* Service boundary owns transport DTOs and mapping
* In a modular monolith, modules remain isolated and composable

---

== Key Placement Rules (Exceptions / Models / DTOs)

=== Exceptions (Rule of origin)
Place exceptions in the layer that *owns the meaning* of the error.

* *Business / domain exceptions* (validation, rule violations) → **Engines**
* *Use-case / workflow exceptions* (preconditions for a use case) → **Managers**
* *Infrastructure exceptions* (timeouts, connectivity, serialization) → **ResourceAccess**
* *Transport/API exceptions* (400/404 mapping, gRPC status mapping) → **Service**

Guideline:
*Do not leak infrastructure exceptions upward.* Convert them to a stable exception or result type at the boundary between layers.

---

=== Models (Domain Models)
Models that represent business concepts (Order, Product, Customer, Money, ProductId) belong to the **Engine layer** (or a shared domain/contracts project),
because Engines implement business logic and should own the vocabulary.

* Domain Model → **Engines (Domain)**
* Value Objects → **Engines (Domain)**
* Enums that represent business meaning → **Engines (Domain)**

Managers use these models but should not own them.

---

=== DTOs (Data Transfer Objects)
DTOs represent *boundary shapes*.

There are typically 3 DTO categories; keep them separate:

1. *Service/API DTOs* (HTTP request/response, gRPC messages)
   * Owned by **Service** (because they are transport contract shapes)

2. *Integration DTOs* (vendor API payloads, storage SDK shapes)
   * Owned by **ResourceAccess** (because they are implementation details)

3. *Internal contracts* (optional)
   * If you use internal messages/events: keep them in **Contracts** (Option B) or in Managers/Service depending on ownership.

Mapping rules:
* Service DTOs ↔ Domain Models mapping happens in **Service** (or a thin adapter inside Service).
* Integration DTOs ↔ Domain Models mapping happens in **ResourceAccess**.

---

== Option A — Interfaces + Domain in Engines (Most Common)

This option is preferred when:
* Accessors represent **business data needs**
* Engines are the primary consumers
* The system is medium-sized
* You want minimal project count

=== Project Structure (extended)

----
MySystem.sln
|
├─ MySystem.Managers
|   # Use-case orchestration (entry points)
|   # May queue calls to other Managers
|   # May publish events (typically after successful use-case completion)

|       ├─ OrderPlacedEvent.cs
|       └─ PaymentCapturedEvent.cs
|
├─ MySystem.Engines

|   |

|   |
|   ├─ Domain/

|   ├─ RetryPolicy.cs
|   ├─ Clock.cs

└─ MySystem.Service
    # Composition root + transport boundary (HTTP/gRPC/Worker)
    # Wires DI and maps transport to Managers
    # Hosts event handlers that delegate to Managers (subscription adapters)

    ├─ Api/
    |   ├─ Controllers/
    |   |   └─ OrderController.cs
    |   └─ Dtos/

    |       └─ Responses/

    |   └─ ApiExceptionMapper.cs
    |
    └─ DependencyInjection.cs           # composition root (DI registrations)

=== Layer Dependencies

Legend:
* "A -> B" means "A references / depends on B"
* Allowed calls are aligned with closed architecture principles

----
Client
  -> MySystem.Service

MySystem.Service
  -> MySystem.Managers
  -> MySystem.Engines
  -> MySystem.ResourceAccess
  -> MySystem.Utilities

MySystem.Managers
  -> MySystem.Engines
  -> MySystem.Utilities
  -> (calls via interfaces in Engines.Contracts)
     - IOrderAccessor / IInventoryAccessor / IPaymentGateway
     - IEventPublisher

MySystem.Engines
  -> MySystem.Utilities
  -> (defines interfaces in Engines.Contracts, does NOT depend on ResourceAccess)

MySystem.ResourceAccess
  -> MySystem.Engines          (to implement Engines.Contracts + use Domain models)
  -> MySystem.Utilities
  -> external SDKs (SQL/HTTP/EventBus)

MySystem.Utilities
  -> (no project dependencies)
----

Notes:

* Managers may publish events via `IEventPublisher` (defined in Engines.Contracts, implemented in ResourceAccess.Messaging).
* Engines do not publish events.
* ResourceAccess may *receive* events via bus consumer, but inbound event handling and dispatch to Managers is hosted in Service (EventHandlers).

== Option B — Dedicated Contracts Project (Large / Multi-Subsystem)

This option is preferred when:
* Many Managers and Engines depend on the same Accessors
* Multiple subsystems share contracts
* You want strict physical enforcement of DIP
* The system is large or long-lived

== Option C — Modular Monolith (Modules as Subsystems)

This option is preferred when:
* The system is a **single deployable** (monolith)
* You want **strict module boundaries**
* You want most benefits of microservices (isolation, composability) without distributed complexity
* Each module can evolve independently and may be extracted later

=== Core Ideas

* Each module is a *subsystem* with its own internal layers:
  * Managers, Engines, ResourceAccess, Utilities (module-local)
* Modules communicate via:
  * Interfaces in a shared Contracts layer (compile-time)
  * Or asynchronous messages/events (runtime)
* The application entrypoint (Host) is the composition root.

=== Recommended Dependency Rules (Module Isolation)

* Code inside a module can reference only:
  * Its own module projects
  * Shared Contracts (if used)
  * Shared Infrastructure (carefully, ideally via abstractions)
* No module references another module’s ResourceAccess directly.
* Prefer *queued calls between Managers* across modules (conceptually),
  implemented as internal message bus, mediator, or domain events.

=== Option C1 — Per-Module Contracts + Per-Module Domain (Strong Isolation)

Use when modules are independent and domain types are not shared.

==== Project Structure (text)

----

|
├─ src
|  |
|  ├─ Host

|  |   └─ MySystem.Api                (HTTP endpoints + API DTOs)
|  |
|  ├─ Modules
|  |   |
|  |   ├─ Orders

|  |   |   ├─ Orders.ResourceAccess
|  |   |   |   ├─ Sql/SqlOrderAccessor.cs
|  |   |   |   ├─ Sql/SqlOrderRecord.cs           (DB DTO)
|  |   |   |   ├─ Mapping/OrderMapping.cs
|  |   |   |   └─ Exceptions/...
|  |   |   └─ Orders.Utilities
|  |   |
|  |   ├─ Catalog
|  |   |   ├─ Catalog.Managers

==== How DTOs Work in Modular Monolith

* API DTOs live in Host/API project:
  * `MySystem.Api/Dtos/...`
* Mapping from API DTOs to module domain models happens in:
  * API project (thin mapping) OR
  * module-specific facade/adapters exposed by module Managers

Module integration DTOs (vendor/DB) remain inside the module ResourceAccess project.

---

=== Option C2 — Shared Contracts + Shared Domain (When Domain Must Be Shared)

Use when you have truly shared domain types (rare, but sometimes needed).

==== Project Structure (text)

----
MySystem.sln
|
├─ MySystem.Contracts
|   ├─ SharedDomain/Models/...
|   ├─ SharedDomain/Exceptions/...
|   └─ SharedContracts/Interfaces/...
|
├─ Host
|   ├─ MySystem.Host
|   └─ MySystem.Api
|
└─ Modules
    ├─ Orders
    |   ├─ Orders.Managers
    |   ├─ Orders.Engines
    |   └─ Orders.ResourceAccess
    ├─ Catalog
    └─ Payments
----

==== Warning (C2)
Shared domain tends to couple modules. Use only when:
* the shared model is stable
* ownership is clear
* volatility is low

Prefer C1 if possible.

---

== Composition Root in Modular Monolith

In Option C, the composition root is the Host:

* Registers module Managers, Engines, ResourceAccess implementations
* Wires module interfaces to module implementations
* Configures internal messaging/eventing for cross-module calls

Example:

[source,csharp]
----
services.AddOrdersModule();
services.AddCatalogModule();
services.AddPaymentsModule();
----

Each module exposes a single registration entry point.

== Quick Decision Guide

[cols="1,3",options="header"]
|===
| Situation | Recommendation

| Medium system, single domain
| Option A

| Large system, shared accessors/contracts
| Option B

| Single deployable, want strong boundaries + future extraction
| Option C (Modular Monolith)

| Modular monolith with minimal sharing
| Option C1 (preferred)

| Modular monolith with unavoidable shared domain
| Option C2 (use carefully)
|===

---

== One-Sentence Summary

*Option A/B focus on layering within a system; Option C repeats those layers per module, enforcing boundaries inside a single deployable, with Host as the composition root.*
